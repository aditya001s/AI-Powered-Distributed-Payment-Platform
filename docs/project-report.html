AegisPay

AI-Powered Payment Orchestration & Fraud Intelligence Platform
A cloud-native, event-driven digital payment system
built as 13 modules with double-entry accounting,
machine-learning fraud detection and AI-assisted investigation
Project Report
Important scope note. AegisPay is a complete working platform, but it is a simulation. It never connects to a real bank, card network or UPI switch. The payment providers are deliberately simulated so that failures, delays and fallback can be tested on demand. The fraud model is trained on synthetic data. These limits are stated throughout this report because they are a design choice, not a gap.

1. Aim of the Project

The aim of AegisPay is to build a digital payment platform that is correct about money and intelligent about fraud — and to prove both claims with tests rather than assert them.

Most student payment projects store a balance in one table and add or subtract from it. That works until something goes wrong, and then there is no way to answer the only question that matters: where did the money go? AegisPay is built to answer that question at all times. It sets out to solve four problems that every real payment company faces:

  1. Money must never be created or destroyed. Every rupee that moves is recorded twice, in a journal that cannot be edited or deleted, and the books can be proved balanced on demand.
  2. A payment touches many services and any one can fail. If the money is taken but the recording fails, or a provider charges the customer and then goes offline, the system must repair itself rather than leave the customer's money stuck.
  3. Fraud must be caught without blocking honest customers. A machine-learning model scores every payment, and hand-written rules cover the specific attack patterns the model was measured to miss.
  4. A human must be able to understand and overrule the machine. When a payment is held, an analyst gets a written, evidence-cited explanation and the final decision.

2. What the System Does, in Simple Terms

AegisPay is a digital wallet platform. A customer holds money in a wallet and sends it to another wallet — like a person paying a shop. Around that simple action sit the controls that make it trustworthy:

CapabilityWhat it means
WalletsEach user has a balance. Money can be added (deposit), removed (withdrawal) or sent to another wallet.
PaymentsSend money from one wallet to another. The system accepts the request instantly and then processes it safely in the background.
Double-entry ledgerAn accountant's journal. Every movement is written as a matching pair of entries, so the totals must always balance.
Fraud detectionEvery payment is scored by a trained model and checked against 8 rules. Risky payments are stopped and queued for a human.
AI investigationFor high-risk payments the system writes a plain-English report explaining the risk, quoting the fraud policy that applies.
Analyst consoleA web dashboard where staff see payments, risk levels and alerts, and approve or block held payments.
NotificationsThe customer is told what happened by email, SMS (both simulated) and a real in-app inbox.
AnalyticsLive dashboards of payment volumes, risk distribution and settlement speed.

Why these choices

  • Money is stored as whole paise in a long, never a decimal. Computers cannot represent 0.01 exactly in binary floating point, so adding it repeatedly loses money.
  • A separate database per service. One service physically cannot read another's tables, even by mistake. Reporting is rebuilt from the event stream instead.
  • Asymmetric JWT signing (RS256). Only the auth service holds the private signing key; everyone else verifies with the public key. With a shared password-style key, any compromised service could mint an admin token.

4. System Architecture

The platform is made of 13 modules: 10 Java applications, a Python ML service, a React dashboard, and a shared library. Each Java service owns its own database and talks to the others through Kafka events or authenticated internal HTTP calls.

A design principle worth highlighting: the model measures, the platform decides. The ML service returns only a probability — never a decision. Turning a probability into APPROVE / REVIEW / HOLD / REJECT needs the business rules too, and only the fraud service has both. This also means a fraud team can retune a threshold as a configuration change, instead of redeploying a model.

5. How a Payment Works, Step by Step

When a customer sends money, the API replies 202 Accepted almost immediately — meaning "accepted, not finished". The real work then runs as a saga: a sequence of steps that records what it has done, so it can undo its work if a later step fails.

  Customer  ──▶  POST /api/payments  ──▶  202 Accepted (status CREATED)
                        │
                        └─▶ "payment-created" event on Kafka
                                   │
                        payment-orchestrator starts the saga
                                   │
     1. RESERVE_FUNDS   ─▶ wallet-service    make the money unspendable
     2. ASSESS_RISK     ─▶ fraud-service     APPROVE / REVIEW continue
                                             HOLD   → park, wait for a human
                                             REJECT → undo everything
     3. AUTHORIZE       ─▶ provider          choose one, retry, fall back
     4. POST_LEDGER     ─▶ ledger-service    write the books BEFORE money moves
     5. CAPTURE_FUNDS   ─▶ wallet-service    debit payer, credit payee (one transaction)
     6. COMPLETE        ─▶ announce "payment-completed"

Two orderings that carry real weight

  • Reserve before authorising. Asking a provider to charge money the customer does not have wastes the call and causes an avoidable decline. The reservation also stops a second payment spending the same money at the same time.
  • Record in the ledger before moving the money. Money should never move without a record. If the system crashes between the two, the books show a transfer that did not happen — which reconciliation detects and a reversal corrects. The opposite order moves real money with no record of why, which is far worse.

The saga's states

The saga stores its state, and only legal moves between states are allowed:

  STARTED → FUNDS_RESERVED → RISK_ASSESSED → AUTHORIZED → LEDGER_POSTED → CAPTURED → COMPLETED
                   │              ▲
                   ▼              │
               RISK_HELD ─────────┘        (waiting for an analyst)
                   │
             COMPENSATING → FAILED / REJECTED

Once the state reaches CAPTURED there is deliberately no route back to compensation. Undoing a payment whose money has already legitimately moved would hand back funds that were correctly taken, so the only correct direction is forward.

When things go wrong

  • Undo is driven by handles, not by status. Each step saves a receipt (holdId, authorizationId, ledgerTransactionId) the moment it succeeds. If the system crashes after a provider approved a charge but before the status was updated, checking the status would miss the real charge — so the system asks "is there a receipt for this?" instead.
  • A decline is not a failure. A provider saying "no" is returned as an answer; a provider that fails to answer is thrown as a fault. Mixing the two is how a system ends up retrying a decline until it accidentally succeeds, or disabling a healthy provider because customers were short of funds.
  • Lost charges are recovered. If a provider charges the customer and then times out, the saga looks the charge up by its own reference and cancels it before trying another provider.
  • Stuck payments are swept up. A background job finds sagas whose progress stopped and drives them forward again, so a crash mid-payment does not leave money frozen.

6. The Ledger — Why the Money Is Trustworthy

The ledger is the heart of the project's correctness claim. It is a genuine double-entry accounting system, and the rules are enforced by the database rather than by application code that could be bypassed.

GuaranteeHow it is enforced
Nothing can be changed or deletedDatabase triggers reject every UPDATE and DELETE on the journal tables.
Every entry balancesA deferred constraint trigger re-checks at commit time that debits equal credits equal the declared total.
Stored balances cannot driftA CHECK constraint derives each balance from that account's own debit and credit totals.
The same event cannot post twiceEach posting carries a derived unique id such as LTX-PAY-<paymentId>, so a repeated message is recognised as a replay.

A customer's wallet is modelled as a liability — the platform owes the customer their money — so a credit increases a wallet. The report notes this is the single most commonly mis-modelled thing in payment systems.

  Deposit    DEBIT  asset:external-funding:INR    an asset arrived
             CREDIT wallet:WAL-…                  we now owe the customer

  Transfer   DEBIT  wallet:PAYER                  we owe the payer less
             CREDIT wallet:PAYEE                  we owe the payee more

Mistakes are fixed by adding the opposite entry, never by editing. Both entries stay visible and cancel out, because deleting the original would destroy the evidence that it ever happened — which is exactly what an audit needs.

Reconciliation can actually fail. Four independent checks run: the trial balance, stored balances replayed from the journal, each posting's internal integrity, and every account's running-balance chain. It is read-only and never silently repairs anything, because the cause of a discrepancy matters far more than the symptom. The test suite deliberately corrupts the ledger and requires the mismatch to be reported — a check that can only ever return "consistent" would be manufacturing confidence.

7. Fraud Detection

The machine-learning model

Algorithmscikit-learn HistGradientBoostingClassifier, isotonic calibration (3 folds)

Honest reading of these numbers. The model is trained on synthetic data with a deliberately imposed pattern. The scores measure how well the model recovers that pattern — they are not evidence of real-world fraud-detection performance, and the project's own model metadata says so explicitly. Being able to state this clearly is part of the engineering quality.

Why rules exist as well as a model

Not out of distrust — because the model's weaknesses were measured. Recall per attack type at the blocking threshold:

Attack patternModel recallInterpretation
Account takeover0.71Model handles this well
Card testing0.60Reasonable
Mule cash-out0.33Weak — needs a rule
Bust-out0.15Almost entirely missed — needs a rule
Friendly fraud0.00Correctly impossible to detect from payment data

A bust-out is a well-behaved account of a year's standing suddenly sending its largest-ever payment to a brand-new recipient. Feature by feature that is nearly identical to a customer finally buying a car, so the model cannot separate them. A rule can, because it insists on the combination: established history and a large multiple of the previous maximum and a recipient never paid before.

Rules also express things a probability cannot. Travelling 6,000 km in eleven minutes is not a risk score — it is a physical contradiction.

The 8 rules

RuleActionFires when
Confirmed fraud historyReview / BlockAn analyst previously confirmed fraud on this account
Bust-out patternHoldLong history + new recipient + far above the historic maximum
Card-testing velocityHoldMany failures in 24h together with a burst of attempts in 1h
Impossible travelHoldImplied travel speed above 900 km/h since the last payment
New device, high valueReviewUnseen device and a large multiple of the usual amount
Dormant account, large paymentReviewUnused for 90+ days, now sending far above average
Unfamiliar cash-out corridorReviewWithdrawal to a new recipient from an unfamiliar country
First payment unusually largeAdvisoryNo history at all and a large amount

Two further design rules: every rule is evaluated, not just the first to match, because an analyst most wants to know which patterns appeared together; and rules escalate only. A rule can make a verdict more cautious, never less — otherwise adding a rule could let fraud through.

How a held payment is resolved

A HOLD verdict parks the saga at RISK_HELD and extends the hold on the customer's funds. The fraud service raises an alert; an analyst claims it in the dashboard and chooses RELEASE or BLOCK. That decision is written to an append-only table — the database refuses any later edit — and the identity of the decider is read from the verified token, never from the request. The decision is published as an event, and it is the only thing that can un-park the payment.

8. AI Investigation (RAG)

When a payment is scored high-risk, the AI investigation service writes an explanation an analyst can act on. It uses retrieval-augmented generation: it finds the fraud policy documents relevant to this specific payment and writes a narrative that cites them.

  • Knowledge base: 12 fraud-policy documents (account takeover, bust-out, card testing, impossible travel, mule cash-out, evidence standards, and others).
  • Retrieval: documents are split into overlapping chunks and converted to 384-dimension vectors stored in pgvector. Policies are also matched directly by the rule id that fired, which guarantees the right policy is always retrieved.
  • Every citation is verified against what was actually retrieved, so the report cannot quote a document it never read.
  • Privacy by construction: the prompt contains the payment facts, amounts, device and location — but no customer name, email, phone or wallet id.
  • It recommends; it never acts. The service deliberately holds no credential for any write API, and an automated test inspects its fields so that a wallet, ledger or payment client cannot be added later.
Stated honestly: the embedding is signed feature hashing over words and character n-grams — lexical matching expressed as vectors. It is not semantic and will not match a paraphrase. The code says so, and the API reports isSemantic = false. The default report writer makes no outbound network call at all; using a hosted language model is an opt-in path.

9. Security

ControlImplementation
Token signingRS256. Only auth-service holds the private key; the public key is published at a JWKS endpoint for others to verify.
RolesUSER, MERCHANT, FRAUD_ANALYST, ADMIN, SERVICE. Every security chain ends in "authenticated", so a new endpoint is protected by default.

Duplicate protectionThree layers: a Redis fast path, a PostgreSQL primary key as the authority, and a derived natural key for money operations.

Browser safetyAccess token kept in memory only; strict Content-Security-Policy; framing denied. The dashboard holds no secret.
A genuinely notable finding. A transaction-boundary audit discovered that three security controls — account lockout, refresh-token reuse detection and the disabled-account check — had been written correctly but never actually worked: each recorded its decision inside a transaction that was then rolled back, erasing the record. They were fixed by committing security state on a separate transaction, and automated tests now enforce that shape so the bug cannot return. Finding a class of defect that passes ordinary testing is a strong result to present.

Deliberately adversarial tests include: firing two crossing transfers (A→B and B→A simultaneously) and requiring both to succeed, which proves the deadlock-avoidance ordering works; attacking the ledger's immutability triggers with raw SQL; disabling a balance trigger to prove reconciliation really detects corruption; and flushing Redis before replaying a request to prove duplicate protection does not depend on the cache.

11. Benefits of This Design

Correctness you can prove

At any moment the platform can be asked whether its books balance and whether wallet balances agree with the ledger, and it answers with evidence. Because the journal is append-only and enforced by the database, a bug in the application cannot quietly rewrite history.

It survives partial failure

Services crash, networks time out and providers go offline. The saga pattern, the transactional outbox, idempotency at three layers and the recovery sweep mean these produce a recoverable outcome instead of lost money or a frozen balance.

Fraud detection that is measured, not asserted

The project states where the model performs well and where it fails, and fills the measured gaps with rules. That is how fraud systems are actually built, and it is more defensible than a single accuracy figure.

Decisions a human can audit

Every held payment comes with an explanation citing the policy that applies. Every analyst decision is permanently recorded with the identity taken from a verified token. Nothing important happens that cannot be explained afterwards.

Independent, replaceable parts

Each service owns its data and communicates through events, so one can be changed, scaled or rewritten without touching the others. The ML model can be retrained and the thresholds retuned without redeploying the payment path.

Secure by default

Deny-by-default authorisation, asymmetric tokens, short-lived service credentials and an AI service that holds no credentials at all mean a single compromised component cannot escalate into control of the money.

12. Real-World Usefulness

Every mechanism here exists in production payment companies, and the problems it solves are real:

"The app says it paid but the money is gone"Ledger-before-capture ordering plus reconciliation means an inconsistency is detected and corrected rather than discovered by the customer.

The same architecture underlies digital wallets, UPI-style payment apps, card acquirers and payment-service providers. The skills demonstrated — event-driven microservices, distributed transactions, double-entry accounting, applied machine learning and secure API design — map directly onto how payment, fintech and banking systems are built.

13. Honest Limitations

Stating these strengthens the project rather than weakening it, because each is a conscious decision with a reason:

  • No real payment rail. SWIFTPAY, NEXUSPAY and PAYBRIDGE are invented, simulated providers. No bank, card network or UPI switch is contacted. This is deliberate: a simulated provider can be made to fail, hang, decline or lose an acknowledgement on command, which is the only practical way to test the recovery paths.
  • The fraud model uses synthetic data. Its metrics measure recovery of an imposed pattern, not real fraud performance. Real transaction data is not publicly available for good reason.
  • Retrieval is lexical, not semantic. The embedding will not match a paraphrase, and the system reports this rather than implying otherwise.
  • Email and SMS are simulated. The in-app inbox is real; the external channels are not connected to a provider.
  • Single-machine deployment. It runs as 15 Docker containers on one host. A Kubernetes Helm chart exists but a multi-node deployment has not been exercised.

15. Running the Project

The whole platform starts with one command. Services are started in stages so that an 8 GB machine is never overloaded:

  cd c:\Users\adity\ansel
  .\scripts\low-memory.ps1 start          # starts all 15 containers, waits until healthy
  .\scripts\panel-demo.ps1 seed           # creates demo accounts, payments and a fraud alert

  .\scripts\demo-payment.ps1              # makes one live payment end to end
  .\scripts\demo-payment.ps1 -Fraud       # triggers a fraud hold for the analyst workflow

  .\scripts\low-memory.ps1 stop           # stops everything

16. Conclusion

AegisPay demonstrates that a payment platform's hardest problems are not in moving a number from one row to another — they are in staying correct when something fails halfway, proving afterwards that nothing was lost, and making an automated risk decision that a human can understand and overturn.

The project addresses each of those directly: a double-entry ledger whose rules the database itself enforces; a saga that records what it has done so it can undo it; a fraud system that measures its own blind spots and covers them with rules; and an AI layer that explains its reasoning with citations while holding no power to act. All of it is backed by 1,940 automated tests, including integration tests against real PostgreSQL and Kafka, and it runs within 2.9 GiB on an ordinary 8 GB laptop.

Equally deliberate is what the project refuses to claim. The providers are simulated, the fraud model is trained on synthetic data, and the document retrieval is lexical rather than semantic — each stated plainly in the code and in this report. Knowing precisely what a system does and does not prove is itself an engineering result.
