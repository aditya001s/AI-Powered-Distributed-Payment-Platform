# Phase 10 release platform with an unbootable bundled PostgreSQL

Phase 10 closes the prior auth-secret, environment-selection, chart/image alignment, shell-injection, security-gating, frontend-promotion, managed-service security, database-isolation, AI-key, and monitoring-isolation findings. The release still cannot ship as a self-contained installation because bundled PostgreSQL cannot create its Unix socket under the enforced read-only root filesystem. Four defense-in-depth and operability gaps also remain around Secret rotation, internal OAuth attribution, Kafka outage visibility, and artifact identity. **Watch for:** **BLOCKER — confirmed:** bundled PostgreSQL exits before accepting connections; **MEDIUM — confirmed:** data-plane credentials do not rotate with `runtimeSecret.version`; **MEDIUM — confirmed:** all internal callers share one OAuth principal; **MEDIUM — confirmed:** Kafka outages leave JVM pods ready without a direct alert; **MEDIUM — confirmed:** deployment trusts mutable SHA tags and detached SBOM files; **LOW — confirmed:** Phase 10 status remains stale.

**Verdict**: NEEDS_CHANGES

## High-level view

The chart's default self-contained topology is structurally valid but not runnable. PostgreSQL uses `/var/run/postgresql` while the StatefulSet makes the root filesystem read-only and mounts only the data and initialization paths, so every database-dependent workload remains behind its init wait (**BLOCKER — confirmed**).

`runtimeSecret.version` now rolls application and monitoring Deployments, but excludes the PostgreSQL and Redis StatefulSets. PostgreSQL role passwords also come only from first-boot initialization, so rotation requires more than restarting the pod (**MEDIUM — confirmed**).

Service authentication still distributes one client ID and secret to every authenticated caller. Audit records cannot identify the calling workload, and one leak grants the shared internal authority (**MEDIUM — confirmed**).

Kafka-dependent applications probe broker availability only before startup. Their shared readiness group excludes Kafka and Prometheus has no broker or consumer-availability alert, leaving post-start outages fail-open without an explicit operational signal (**MEDIUM — confirmed**).

The release chain is source-aligned at a full commit SHA, but deployed OCI references are tags and the generated SBOM is retained only as a workflow artifact. Registry mutation can change deployed bytes without changing the deployment input, and the SBOM is not bound to those bytes (**MEDIUM — confirmed**).

## Bundled PostgreSQL cannot create its runtime socket

**BLOCKER — confirmed.** `infrastructure/kubernetes/aegispay/templates/data-plane.yaml:68-108` runs PostgreSQL as UID/GID 999 with `readOnlyRootFilesystem: true`, while its only mounts are `/var/lib/postgresql/data` and `/docker-entrypoint-initdb.d`. PostgreSQL 17 defaults `unix_socket_directories` to `/var/run/postgresql`; an exact container smoke using the chart's user and filesystem settings initialized the data directory and then exited with `FATAL: could not create lock file "/var/run/postgresql/.s.PGSQL.5432.lock": Read-only file system`. Add an `emptyDir` at `/var/run/postgresql` writable by group 999, or configure another explicit writable ephemeral socket mount. Add a bundled-topology startup smoke because Helm lint and kubeconform cannot detect process-level filesystem requirements.

## Secret rotation stops at the data-plane boundary

**MEDIUM — confirmed.** Application pods carry `aegispay.io/runtime-secret-version` in `templates/applications.yaml:24-27`, and monitoring Deployments carry it in `templates/monitoring.yaml:65-68,134-137,188-191,254-257`; the StatefulSet pod templates in `templates/data-plane.yaml:67-108,148-178,231-274` do not. Rotating `REDIS_PASSWORD` rolls clients onto the new value while Redis keeps the old one. PostgreSQL's initializer creates roles only on first boot (`data-plane.yaml:13-35`), so a restart does not apply changed service passwords to existing roles. Add the version annotation to Secret-consuming StatefulSets and a coordinated hook, job, or documented procedure that executes `ALTER ROLE` before clients roll; test against an existing PVC.

## Internal calls still collapse onto `aegis-internal`

**MEDIUM — confirmed.** Helm publishes one `applicationConfig.internalClientId` globally (`values.yaml:200`; `templates/configmap.yaml:53`) and injects the same `INTERNAL_CLIENT_SECRET` into every `serviceAuth` workload (`templates/applications.yaml:143-147`; `secrets.template.yaml:25`). Compose repeats the contract in `.env.example:96-98`. Since auth tokens use the client ID as `sub`, logs cannot distinguish wallet-service from payment-orchestrator, and compromise of one caller impersonates all callers. Define per-service IDs and Secret keys, seed each client in auth-service, inject only the matching credential, and narrow scopes where internal APIs permit it.

## Kafka failures after startup remain outside health and alerts

**MEDIUM — confirmed.** `templates/applications.yaml:49-61` waits for bundled Kafka only in an init container, while shared readiness is `readinessState,db,redis` in `platform-common/src/main/resources/aegis-defaults.yml:188-197`. Prometheus rules in `templates/monitoring-config.yaml:65-113` alert on exhausted outbox/DLT retries and lost scrape targets, but not broker availability, producer connectivity, consumer lag, or stalled event flow. Add a bounded Kafka health contributor to readiness, or document deliberate fail-open behavior and add direct broker/exporter plus lag or event-staleness alerts; do not add Kafka to liveness.

## SHA tags and SBOM artifacts do not bind deployed bytes

**MEDIUM — confirmed.** `_helpers.tpl:35-41` renders `repository:<global tag>`, `images.yml:76-110` pushes the commit-SHA tag, and `deploy.yml:11-14,83-94,121-134` accepts it as the release coordinate. A SHA-shaped tag remains mutable in OCI. The SPDX output is uploaded separately for 90 days (`images.yml:97-108`) with no OCI attachment, signature, provenance, or deploy-time verification. Record each published digest in a signed release manifest, render `repository@sha256:…` per service, attach SBOM/provenance attestations to each digest, and verify them before installing kubeconfig.
